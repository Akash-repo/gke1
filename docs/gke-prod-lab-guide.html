00

How to use this lab

Two kinds of steps appear below. console steps are clicked through in the GCP Console, as you asked — that's where the architecture decisions live and where exam questions are usually framed. cloud shell steps are commands — pushing images and applying Kubernetes YAML has no console equivalent, so those run in Cloud Shell (the terminal built into the console itself, top-right icon — no local setup, already authenticated as you).

Already true

gke1 and gke2 are already committed to GitHub, and both already build into working local Docker images (gke1:local, gke2:local) that call each other correctly. This lab wires the same two containers into GKE — nothing about the app code changes.

Cost & teardown

Every resource here bills hourly the moment it exists — the cluster's control plane, the nodes, the NAT gateway, and above all the load balancer's forwarding rule. Phase 13 is a full teardown checklist; run it the same day once you've validated the deployment.

01

New project, billing, APIs

A dedicated project is a hard billing and IAM boundary — the cheapest possible teardown is gcloud projects delete, which nukes everything inside it in one shot, no matter what you forgot to clean up manually.

console
  1. Console → project picker (top bar) → New Project. Name it something you'll recognize as disposable, e.g. gke-lab-2026.
  2. Billing account → link the project to your billing account (required before any compute resource can be created).
  3. APIs & Services → Enable APIs and Services, enable each of: compute.googleapis.com, container.googleapis.com, artifactregistry.googleapis.com.
Exam angle

The Associate Cloud Engineer exam tests project/folder/org IAM boundaries directly. Know that IAM roles granted at the project level inherit down to every resource inside it, and that deleting a project is the only GCP action that's both total and irreversible after a 30-day grace window.

02

Custom VPC & VPC-native subnet

Auto-mode VPCs hand you one subnet per region with ranges you don't control — fine for a demo, disqualifying for production, since a VPC-native GKE cluster needs you to reserve two extra IP ranges per subnet before the cluster exists: one for pods, one for Services.

console
  1. VPC network → Create VPC network. Subnet creation mode: Custom — never Auto for anything you'd call production.
  2. Add a subnet with these exact values:
FieldValue
Namegke-subnet
Regionus-central1
Primary IP range (nodes)10.10.0.0/20
Secondary range — podsgke-pods · 10.20.0.0/14
Secondary range — servicesgke-services · 10.30.0.0/20
Private Google AccessOn
Exam angle

Private Google Access and Private nodes are different knobs that get conflated constantly. Private Google Access lets resources without an external IP reach Google APIs (Artifact Registry, Logging, Storage) directly, without NAT. It does nothing for reaching the general internet — that's Cloud NAT's job, next phase. A private GKE cluster needs both.

03

Cloud Router + Cloud NAT

Private nodes have no external IP by design — that's the whole point of "private." But docker pull from Artifact Registry, OS package updates, and any outbound call your app makes to the public internet still need some way out. Cloud NAT is that way out, and it's the single most common thing people forget when standing up a private cluster — the symptom is pods stuck on ImagePullBackOff with no obvious cause.

console
  1. VPC network → Cloud Routers → Create router. Name gke-router, network gke-vpc, region us-central1.
  2. Network Services → Cloud NAT → Create NAT gateway. Attach it to gke-router. Under NAT mapping, choose Custom subnet IP ranges and explicitly select gke-subnet — including its secondary pod range. If you leave the pod range unchecked, pods silently get no NAT translation while nodes do.
Interview angle

"How do private GKE nodes pull container images?" is a near-guaranteed interview question once "private cluster" is on your resume. The answer has two parts: Artifact Registry traffic can go out via Private Google Access alone; anything else needs Cloud NAT with the pod IP range explicitly included in the NAT mapping.

04

Firewall rules

A custom-mode VPC starts with zero allow rules — only the two implied rules every VPC has (deny all ingress, allow all egress). GKE itself auto-manages the rules its control plane needs to reach nodes, and the Ingress controller auto-manages the health-check rule for whatever Service it's pointed at. What's left for you is debug access to nodes that have no public IP.

console
  1. VPC network → Firewall → Create firewall rule: name allow-iap-ssh, direction Ingress, targets: all instances in the network, source range 35.235.240.0/20 (Google's fixed IAP range), protocols/ports tcp:22.
Interview angle

"Your GKE nodes have no external IP — how do you SSH into one to debug it?" Answer: Identity-Aware Proxy (IAP) TCP forwarding — gcloud compute ssh <node> --tunnel-through-iap. IAP proxies the connection through Google's infrastructure over HTTPS, so the node never needs a public IP or an open port to the internet — only to Google's own 35.235.240.0/20 range.

05

Artifact Registry

Container Registry (gcr.io) is the legacy product; Artifact Registry is its regional, IAM-scoped, multi-format successor and what GCP now provisions by default. Pinning images to the same region as your cluster keeps pulls fast and free of cross-region egress cost.

consolecloud shell
  1. Artifact Registry → Create repository. Name gke-repo, format Docker, mode Standard, region us-central1.
  2. Open Cloud Shell and authenticate Docker against it, then tag and push the images you already built locally:
Cloud Shell — from your gke1 and gke2 project folders
# one-time: let docker push to this region's Artifact Registry
$ gcloud auth configure-docker us-central1-docker.pkg.dev

# from wherever gke1:local and gke2:local exist, or rebuild here
$ docker tag gke1:local us-central1-docker.pkg.dev/PROJECT_ID/gke-repo/gke1:v1
$ docker tag gke2:local us-central1-docker.pkg.dev/PROJECT_ID/gke-repo/gke2:v1

$ docker push us-central1-docker.pkg.dev/PROJECT_ID/gke-repo/gke1:v1
$ docker push us-central1-docker.pkg.dev/PROJECT_ID/gke-repo/gke2:v1

Swap PROJECT_ID for your new project's ID throughout this guide.

06

A dedicated node service account

Left unset, new node pools default to the project's Compute Engine default service account — which typically carries the broad, legacy Editor-adjacent scope. Every workload on every node inherits whatever that account can do. A minimal, purpose-built node SA is one of the highest-leverage production hardening steps in GKE, and one of the most common things a real security review flags.

console
  1. IAM & Admin → Service Accounts → Create service account: gke-node-sa.
  2. Grant it exactly these project roles — nothing else:
RoleWhy the node needs it
roles/logging.logWritership container logs to Cloud Logging
roles/monitoring.metricWritership metrics to Cloud Monitoring
roles/monitoring.viewerread back its own metrics for autoscaling signals
roles/artifactregistry.readerpull images from gke-repo
Exam angle

This is the node's identity — separate from Workload Identity, which governs what individual pods can do. Both appear on the GKE section of every associate and professional GCP exam; conflating them is the single most common wrong answer.

07

The GKE cluster

Every toggle below is a deliberate production trade-off, not a default left alone. This is the phase worth reading twice before clicking Create.

console
  1. Kubernetes Engine → Clusters → Create → switch the mode at the top from Autopilot to Standard.
  2. Cluster basics: name gke-cluster; location type Regional, region us-central1 — a regional cluster runs the control plane redundantly across three zones, so a single zone outage doesn't take your API server down with it.

Trade-off — control plane access

True production practice keeps the control plane's public endpoint off entirely and reaches it only from inside the VPC — via a bastion host, Cloud VPN, or Interconnect. That's not practical for a same-day learning lab run from Cloud Shell. For this lab: keep the public endpoint on, and under Control plane authorized networks add your current public IP (or Cloud Shell will simply be rejected). Say this trade-off out loud in an interview — knowing what you're not doing, and why, is the actual signal.

Cost note — regional × autoscaling

A regional cluster provisions its node pool per zone. "1–3 nodes" here means 1–3 nodes in each of three zones — 3 to 9 e2-medium VMs total. That's the right default to know for the exam; it's also why this lab tears down the same day.

08

Connect & deploy the workloads

The manifests below already live in each repo's k8s/ folder — they're the same shape you'd use in a real GitOps pipeline, just applied by hand this once. Both services run in a dedicated apps namespace with their own minimal ServiceAccount (not default) — namespace isolation and per-workload identity are both things a resource quota or an RBAC policy can later hang off.

cloud shell
Cloud Shell
# point kubectl at the new cluster
$ gcloud container clusters get-credentials gke-cluster \
    --region us-central1 --project PROJECT_ID

# clone both repos (or paste the k8s/ files directly)
$ git clone https://github.com/Akash-repo/gke1.git
$ git clone https://github.com/Akash-repo/gke2.git

# update the image references first — see below
$ kubectl apply -f gke1/k8s/namespace.yaml
$ kubectl apply -f gke2/k8s/serviceaccount.yaml -f gke2/k8s/deployment.yaml -f gke2/k8s/service.yaml
$ kubectl apply -f gke1/k8s/serviceaccount.yaml -f gke1/k8s/deployment.yaml -f gke1/k8s/service.yaml

Each deployment.yaml has a placeholder image: REGION-docker.pkg.dev/PROJECT_ID/gke-repo/gke1:latest. Edit it to the exact tag you pushed in Phase 05 (us-central1-docker.pkg.dev/PROJECT_ID/gke-repo/gke1:v1) before applying — an unpinned :latest tag is itself worth flagging as an anti-pattern in a real review: it makes rollbacks ambiguous, since the tag doesn't tell you which build is actually running.

What's already in the manifests

Resource requests/limits on every container (so the scheduler can bin-pack correctly and one runaway pod can't starve its neighbors), a readinessProbe and livenessProbe both pointed at /is-alive (readiness gates traffic into the pod; liveness restarts it if it wedges), and automountServiceAccountToken: false since neither app calls the Kubernetes API and doesn't need that token mounted.

09

Expose gke1 & test end-to-end

gke2 stays ClusterIP — reachable only from inside the cluster, which is correct: it has no reason to ever see a request that didn't come from gke1. gke1 gets an Ingress, which GKE turns into a real Google Cloud external HTTP(S) load balancer wired directly to gke1's pod IPs.

cloud shellconsole
$ kubectl apply -f gke1/k8s/ingress.yaml

# provisioning a real GCLB takes several minutes — watch for an address
$ kubectl get ingress gke1-ingress -n apps --watch
  1. Once an ADDRESS appears, Console → Kubernetes Engine → Gateways, Services & Ingress will show the same Ingress with a green healthy backend once health checks pass.
  2. Test both hops from your own machine, not just Cloud Shell — this confirms the public path actually works:
$ curl http://EXTERNAL_IP/is-alive
OK

$ curl http://EXTERNAL_IP/call-gke2
gke2 running on gke2-7d8f9c6b8f-x2kqp   ← the actual pod name, since $HOSTNAME is the pod
What this proves

The container-native load balancer reached a specific gke1 pod directly (not a node), that pod resolved http://gke2:8083 through cluster DNS to a gke2 Service, and that Service load-balanced to one of two gke2 pod replicas — the exact same call chain you validated locally with Docker, now running across real GCP networking, IAM, and load balancing.

10

Verify autoscaling

gke1/k8s/hpa.yaml is already applied conceptually here — a HorizontalPodAutoscaler that keeps gke1 between 2 and 5 replicas, scaling on CPU. This is the mechanism behind "GKE scales with traffic," and interviewers will ask you to explain what actually triggers it.

cloud shell
$ kubectl apply -f gke1/k8s/hpa.yaml
$ kubectl get hpa gke1 -n apps --watch
Exam angle

Three distinct autoscalers exist in GKE and the exam expects you to tell them apart: HPA changes replica count based on pod metrics (CPU here); Vertical Pod Autoscaler changes a pod's requested CPU/memory instead of its count; Cluster Autoscaler — the "1–3 nodes" setting from Phase 07 — adds or removes nodes when pods can't be scheduled. HPA scaling replicas is what eventually triggers Cluster Autoscaler to add a node, not the other way around.

11

Observability, for free

Because the node SA from Phase 06 was granted logging and monitoring roles, every container's stdout/stderr and every standard resource metric is already flowing — no agent to install, nothing extra to deploy.

console
  1. Kubernetes Engine → Workloads → gke1 → Logs tab: live container logs, filterable by pod.
  2. Logging → Logs Explorer, filter resource.type="k8s_container" AND resource.labels.namespace_name="apps" to see both services' logs together.
  3. Monitoring → Dashboards → GKE: per-pod CPU/memory against the requests/limits you set in Phase 08 — this is where you'd notice a limit set too low before it pages anyone.

13

Teardown

Delete in this order — the load balancer's forwarding rule and the NAT gateway both hold references that block deleting what's underneath them, so working top-down avoids "resource in use" errors.

cloud shellconsole
  • 1kubectl delete -f gke1/k8s/ingress.yaml — releases the external IP and forwarding rule first; deleting the cluster first can orphan the load balancer.
  • 2Kubernetes Engine → Clusters → delete gke-cluster.
  • 3Network Services → Cloud NAT → delete the NAT gateway, then VPC network → Cloud Routers → delete gke-router.
  • 4VPC network → delete gke-subnet, then delete gke-vpc itself.
  • 5Artifact Registry → delete gke-repo (drops the pushed images).
  • 6Simplest total cleanup: IAM & Admin → Settings → Shut down the whole project — guarantees zero residual billing regardless of what step 1–5 missed.
Local Docker validation for this same gke1/gke2 pair — is-alive checks and the gke1 → gke2 call chain — is already confirmed working before this lab begins.
