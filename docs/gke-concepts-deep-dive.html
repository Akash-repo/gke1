Compute layer
01

Node → kubelet → Pod → Container

Confirming your own instinct: yes — a node really is just a VM, and it really does host your pods. Here's the full chain underneath that sentence.

The analogy

A node is an apartment building — a real, physical Compute Engine VM with its own street address. The kubelet, running on that VM, is the building superintendent: it takes orders from city hall (the control plane — "these are the units that should exist here") and is the only one who actually turns a key to start or stop anything. A Pod is one apartment unit — one lease, one address, one shared front door. The container(s) inside it are the roommates living in that unit: each has their own room, but they share the unit's one address and can reach each other down the hall (localhost) without ever stepping outside.

Today, gke1's Deployment runs replicas: 2 — that's exactly two Pod objects like the ones above, each with one gke1 container, scheduled onto whichever node(s) in the 3–9-VM node pool have room. A node routinely hosts pods from many unrelated Deployments at once; nothing about a node is dedicated to one app.

Confirmed

"A node is a VM that hosts pods" is exactly right. One VM (node) hosts many apartment units (pods); each unit houses one or more roommates (containers) who share that unit's one address.

  • A Pod, not a container, is the smallest thing Kubernetes schedules and gives an IP to — containers inside one pod share that IP and localhost.
  • kubelet is the only component that talks to both the control plane above it and the container runtime below it — the node-local enforcement point, not a scheduler itself.
  • In GKE Standard, "node" always means a real Compute Engine VM — there's no nested virtualization here.
  • Multiple containers per pod exist for tightly-coupled cases (a sidecar sharing the same network/volumes), not for unrelated services — Deployments and Services are the tool for that.
Exam & interview questions
Why would two containers in the same pod talk over localhost instead of a Service DNS name?

They share one network namespace — one IP — because they're both inside the same "apartment." localhost:PORT reaches the roommate directly; no DNS lookup or Service object is involved.

If a node dies, what happens to the pods that were on it?

They're gone with it — the apartment building itself is gone. The Deployment controller notices the replica count dropped and schedules replacement pods on a different node; nothing "moves" a running pod between nodes.

Network layer
02

The three VPC-native IP ranges

Every VPC-native GKE subnet carves out three separate IP pools, each answering a completely different question — and the sizing decision is effectively permanent once the cluster exists.

The analogy

The subnet is the whole apartment complex. The primary range is the buildings' own street addresses — one per building (node) — small, because there are only ever a handful of buildings. The secondary pod range is enormous because the developer pre-reserves an entire floor of mailboxes — a full block of 256 — for every building the moment it's built, whether or not that building ever fills a fraction of them; pre-reserving the whole floor lets each building's own superintendent assign addresses instantly, with zero phone calls to head office. The secondary service range isn't a location at all — it's the complex's internal phone directory. Dialing an extension doesn't ring a physical desk; it rings whoever's on duty for that team right now.

RangeValueAnswers
Primary — nodes10.10.0.0/20Which VM is this?
Secondary — gke-pods10.20.0.0/14Which pod is this?
Secondary — gke-services10.30.0.0/20Which Service (virtual, stable) is this?

The node pool autoscales to at most 9 nodes total (3 zones × 3). At 9 nodes × one reserved /24 each, that's 2,304 addresses actually spoken for — out of 262,144 reserved in gke-pods. The headroom is deliberate, not wasteful.

Mental model

Two of the three ranges are real, routable VPC addresses (node, pod); the third is virtual — a Service IP is never assigned to any interface anywhere, purely a routing construct that the dataplane resolves to a real pod IP on every request.

  • GKE reserves a full /24 (256 IPs) per node from the pod range by default, regardless of how many pods actually run there — that single fact is why the pod range must be this large.
  • All three ranges live on the same subnet, as primary + two secondary ranges — that's what "VPC-native" means mechanically.
  • Secondary ranges are effectively fixed once the cluster is running — under-sizing the pod range is the classic "can't add more nodes" failure, fixed by planning generously upfront, not by resizing later.
Exam & interview questions
Why is the pod range a /14 when the node range is only a /20?

Because pod IPs are allocated in whole /24 blocks per node up front, not per actual pod — the range needs enough /24 blocks for every node the cluster could ever scale to. A /14 supports over a thousand such blocks, deliberately oversized for headroom.

Can a Service and a running pod ever collide on the same IP?

No — the service range is a disjoint secondary range from the pod range specifically so a real pod address and a virtual Service address can never collide.

Network layer
03

VPC-native vs routes-based

This is the setting that made the ranges in §02 possible — and it's why the Console no longer even offers the older model for a new Standard cluster.

The analogy

Routes-based (legacy): the postal service only ever delivers to a building's front desk — the node's IP. It has no idea individual apartment units exist. Every building keeps its own private forwarding chart, and every time a new building goes up, the citywide routing office manually adds an entry: "mail for units 1–256 in that new building → forward via its front desk." VPC-native (alias IP): every unit gets its own real, city-registered street address, baked directly into the official city address book the moment the complex is platted — the pod secondary range from §02. Any city service that reads that same book — firewall rules, VPC peering, Cloud NAT — can now route straight to one specific unit, no building's private chart required.

  • Routes-based clusters needed one manual VPC route per node for its pod range; VPC-native needs zero — the subnet's secondary range is the route.
  • Only VPC-native pod IPs are visible to VPC firewall rules and VPC peering directly — routes-based pod traffic couldn't be firewalled or peered at the pod-IP level.
  • "Alias IP range" is the literal GCP feature name behind "VPC-native" — expect the exam to use both terms interchangeably.
  • New GKE Standard clusters default to, and in practice require, VPC-native today.
Exam & interview questions
What breaks if you try to write a firewall rule targeting a pod IP range on a legacy routes-based cluster?

Nothing to target — the VPC never sees pod IPs as real addresses on routes-based clusters, so firewalling and peering can only act at the node level.

Is VPC-native still optional for a new GKE Standard cluster?

Not in practice — it's the default and effectively the only supported networking mode for new clusters today.

Network layer
04

Private nodes + Cloud NAT

"Private" means the node has no external IP — full stop. That still leaves the question of how it pulls a container image at all.

The analogy

The building has no public entrance visible from the street — no external IP. But deliveries still have to leave sometimes. The complex has exactly one shared loading dock (Cloud NAT), watched by a dock manager (Cloud Router), that lets a truck leave, run its errand, and come back without ever exposing any single building's internal address to the outside world. Separately, there's a private courier tunnel straight to a few pre-approved city offices (Google APIs — Artifact Registry, Logging, Monitoring) that never touches the public road at all — that's Private Google Access, a completely different mechanism from the loading dock, even though both let a private building "reach outside."

  • Private Google Access and Cloud NAT solve two different problems — the former reaches only Google APIs, the latter reaches the general internet — and a private cluster needs both.
  • Cloud NAT's subnet mapping must explicitly include the pod secondary range, or pods silently get no egress while the node itself does.
  • Private nodes have no external IP, ever — not even ephemeral.
  • Debugging a private node goes through Identity-Aware Proxy (IAP) TCP forwarding, not the node's own address.
Exam & interview questions
A private node pulls from Artifact Registry fine, but a pod's outbound curl to an external API times out — what's wrong?

Cloud NAT is either not attached to the subnet, or its mapping excludes the pod secondary range. Artifact Registry can ride Private Google Access alone; a general internet call needs NAT specifically.

How do you debug a private node with no public IP?

gcloud compute ssh <node> --tunnel-through-iap — IAP proxies the session over HTTPS through Google's own infrastructure; the node never needs a public IP or an open port.

Identity layer
05

The node service account

Every VM needs some Google Cloud identity to act as. Left unset, that identity defaults to something far broader than you'd want.

The analogy

Every building is issued one shared facilities master key at move-in — gke-node-sa — held by kubelet, the container runtime, and by default every pod living there, since they all currently exit through the same door. That one key opens exactly four doors and nothing else: the logging drop-box, two monitoring rooms, and the loading-dock's package-pickup counter — deliberately not the master key to the whole city.

RoleWhy the node needs it
roles/logging.logWritership container logs to Cloud Logging
roles/monitoring.metricWritership metrics to Cloud Monitoring
roles/monitoring.viewerread back its own metrics for autoscaling signals
roles/artifactregistry.readerpull images from gke-repo
Mental model

The node SA is a VM-level identity — what the node itself, and by default every pod on it, presents to Google Cloud APIs. It's not about your app's logic at all; it's what lets the node do its own job.

  • Left unset, a new node pool defaults to the project's Compute Engine default service account, which typically carries broad legacy scope — the first thing a real security review flags.
  • Minimal roles here directly bound the blast radius of a compromised node to exactly these four capabilities, not project-wide access.
Exam & interview questions
What can an attacker do with a shell on a compromised node, given this SA?

Write logs/metrics and read from Artifact Registry — nothing else. They cannot read Cloud Storage buckets or touch IAM, because the SA was never granted those roles.

Why does the node need monitoring.viewer in addition to monitoring.metricWriter?

To read back its own emitted metrics as autoscaling signals, not just write them one-way.

Identity layer
06

Node SA vs Workload Identity

The shared master key from §05 works, but it has one structural problem: it's the same key for every tenant in the building.

The analogy

Workload Identity is what happens when the building switches every tenant company (pod) over to its own individually-keyed employee badge, mapped one-to-one to that specific tenant's own access list. Losing one employee's badge only exposes what that one tenant could do — never the whole building's facilities access.

Grounded in this cluster — stated honestly

Workload Identity is enabled at the cluster level (PROJECT_ID.svc.id.goog), and both gke1-ksa and gke2-ksa exist as dedicated per-service Kubernetes ServiceAccounts. But neither serviceaccount.yaml carries an iam.gke.io/gcp-service-account annotation today — because neither app currently calls a GCP API. The plumbing (dedicated KSAs) exists; the wiring (a GSA binding) doesn't, because nothing needs it yet.

  • Node SA is one identity shared by everything on the VM; Workload Identity is a distinct identity per pod (technically per KSA), federated through IAM — two separate layers, not two settings of the same thing.
  • Workload Identity needs two matching halves: the pod's serviceAccountName (a KSA) and an IAM binding on a GSA — either half missing means the pod falls back to the node's identity.
  • Confusing node SA with Workload Identity is called out on the lab guide itself as the single most common wrong answer on GKE exam questions.
Exam & interview questions
A pod's serviceAccountName is set, but GCP API calls still return the node's broad identity — why?

The KSA almost certainly lacks the iam.gke.io/gcp-service-account annotation, or the GSA is missing the roles/iam.workloadIdentityUser binding for that KSA. Without both halves, requests silently fall through to the node's default identity.

If gke1 later needed to read a Secret Manager secret, what's the minimum-privilege way to grant that?

Create a GSA scoped to only that secret's access role, and bind it to gke1-ksa via Workload Identity — granting it on gke-node-sa instead would hand that same access to gke2 and every other pod sharing that node pool.

Orchestration layer
07

The manifest apply sequence

Why namespace.yaml comes first, why gke2's trio comes before gke1's, and what the API server actually does with each object.

The analogy

You can't legally issue an employee ID badge (ServiceAccount) to a department that doesn't exist in the org chart yet (Namespace). You can't seat someone at a desk (Deployment) without first issuing them a badge, since the desk-assignment form requires a valid badge number. The company directory (Service) only becomes useful once desks are filled — but unlike the badge, nothing stops you from printing the directory page before the desk is occupied; it just stays empty until someone's assigned there.

The actual commands, in order
$ kubectl apply -f gke1/k8s/namespace.yaml
$ kubectl apply -f gke2/k8s/serviceaccount.yaml -f gke2/k8s/deployment.yaml -f gke2/k8s/service.yaml
$ kubectl apply -f gke1/k8s/serviceaccount.yaml -f gke1/k8s/deployment.yaml -f gke1/k8s/service.yaml
Mental model

Kubernetes is declarative and eventually-consistent almost everywhere — except at the exact points where one object's spec hard-references another by name. Namespace and ServiceAccount are two of those hard references; that's the whole reason this order exists.

  • The API server rejects a Pod/Deployment referencing a ServiceAccount or Namespace that doesn't exist yet — an enforced admission-time failure, not a soft Pending state.
  • kubectl itself enforces no order between unrelated objects — nothing technically stops applying gke1's trio before gke2's; deploying the callee first is a design discipline, not a hard requirement.
  • A Service can be applied before any matching pod exists — it just has zero endpoints and routes nowhere until a pod with a matching label passes readiness.
  • A dedicated ServiceAccount per workload (not default) is identity-and- policy plumbing laid down even when nothing consumes it yet — see §06.
Exam & interview questions
You apply a Deployment before the ServiceAccount it references exists — what actually happens?

The API server's ServiceAccount admission control rejects Pod creation outright with an explicit "serviceaccount not found" error — not a soft failure, not a Pending pod, the object creation itself is refused.

Does applying gke2's manifests first guarantee its pods are Ready before gke1's pods are created?

No — it only guarantees the objects exist first, not that they're ready. That's why gke1's readiness/liveness probes and ordinary retry behavior on its call to GKE2_URL matter independently of apply order.

Traffic layer
08

Container-native load balancing (NEG)

How a request from the public internet actually finds one specific gke1 pod, out of however many are currently running.

The analogy

In a traditional building (instance-based/NodePort load balancing), a caller reaches whichever building's front desk answers — a node's NodePort — and the operator (kube-proxy, via iptables rules) looks up which unit to forward to, sometimes a unit in an entirely different building, meaning the call gets relayed a second time. With container-native load balancing (a NEG), the caller has the complex's real-time smart directory — the exact unit's address is looked up once, up front, and the call goes straight there, skipping every front desk and every relay.

gke1's Service carries the annotation that makes this real:

metadata:
  annotations:
    cloud.google.com/neg: '{"ingress": true}'

and its Ingress backend points straight at that Service on port 80 → container port 8082. gke2 has neither — it stays ClusterIP-only, correctly unreachable from outside the cluster.

  • NEG membership is pod IPs, kept live as pods are created or terminated — health checks target pods directly, not nodes.
  • Container-native LB removes kube-proxy from the request path for Ingress traffic — kube-proxy still does its job for ClusterIP-to-ClusterIP traffic, like gke1 → gke2.
  • The cloud.google.com/neg annotation on the Service is what tells GKE's Ingress controller to provision a NEG instead of the older instance-group backend.
Exam & interview questions
How does traffic actually get from GCLB to a specific gke1 pod?

The Ingress controller provisions the LB's backend as a Network Endpoint Group populated with gke1's live pod IPs — because of the Service's cloud.google.com/neg annotation — so the LB dials the pod IP directly. No node IP, no kube-proxy, in that specific path.

Does gke1's call to gke2 also go through a NEG?

No — that's ClusterIP-to-ClusterIP traffic inside the cluster, resolved by cluster DNS and load-balanced by kube-proxy. NEGs are specifically the Ingress/GCLB-to-pod path for external traffic.

Scaling loop
09

HPA vs VPA vs Cluster Autoscaler

Three different autoscalers, operating on three different axes, chained together in one direction only.

The analogy

Three different staffing decisions, made by three different people. HPA is a team lead hiring more staff onto an existing team once each person's workload crosses a threshold — more replicas doing the same job. VPA is facilities quietly giving each existing staff member a bigger desk instead of hiring anyone new — right-sizing a pod's own CPU/memory request. Cluster Autoscaler is the landlord leasing an entirely new building only when every existing one is completely full and there's no floor space left to seat a new hire, no matter how badly the team lead wants to.

The real numbers, from gke1/k8s/hpa.yaml and the node pool config: minReplicas: 2, maxReplicas: 5, target CPU averageUtilization: 60; node pool autoscaling 1–3 nodes per zone across 3 zones (3–9 e2-medium total). No VPA manifest exists in this project today — gke1 and gke2's resource requests/limits (100m/256Mi request, 250m/256Mi limit) are fixed by hand, not VPA-managed.

  • Three autoscalers, three different axes: HPA = replica count; VPA = per-pod resource requests; Cluster Autoscaler = node count.
  • The chain only runs one direction: HPA scaling replicas can trigger Cluster Autoscaler (when pods go unschedulable); Cluster Autoscaler adding a node never itself triggers HPA.
  • Don't run HPA and VPA watching the same metric — they fight each other. If combined, VPA typically manages memory while HPA manages CPU.
  • A regional cluster's "1–3 nodes" is per zone — the real Cluster Autoscaler range here is 3–9 total VMs, not 1–3.
Exam & interview questions
gke1's HPA is maxed at 5 replicas but CPU is still above target — will Cluster Autoscaler add a node?

Only if pods can't be scheduled due to lack of node capacity. If the existing 3–9 nodes have room for those 5 replicas, Cluster Autoscaler does nothing — it reacts to unschedulable pods, not to HPA hitting its own ceiling.

Why not just run HPA and VPA together on CPU for the same Deployment?

They'd both react to the same CPU signal in conflicting ways — HPA adding replicas to spread load while VPA simultaneously resizes the existing pods' CPU requests — producing thrashing rather than a stable target.
